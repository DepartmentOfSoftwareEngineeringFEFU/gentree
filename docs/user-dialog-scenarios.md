# 3.4 Сценарий диалога системы с пользователем

> Актуализировано по коду на текущей ветке (`gleb-dev`). Старая версия главы
> описывала сценарии до появления подсистемы архивных запросов/книги —
> структура UI и часть бизнес-логики с тех пор изменились. Расхождения со
> старой версией откомментированы внутри пунктов.

Сценарии ниже описывают путь обычного пользователя — владельца
генеалогического исследования. Сценарии для ролей генеалога и
администратора (рабочий стол генеалога, панель администратора) — предмет
отдельной главы.

## Сценарий для задачи «Регистрация в системе»

1. Пользователь открывает страницу авторизации и выбирает вкладку
   «Регистрация» (форма входа и форма регистрации находятся на одном
   экране и переключаются вкладками, а не двумя разными окнами).
2. Система отображает форму регистрации.
3. Пользователь заполняет поля формы: адрес электронной почты, пароль,
   а также необязательные имя/фамилию/отчество.
4. Пользователь нажимает кнопку «Зарегистрироваться».
5. Система проверяет корректность введённых данных (формат email, длина
   пароля — не менее 8 символов).
6. Система создаёт учётную запись пользователя с ролью `USER` и статусом
   `ACTIVE`, сохраняет данные в таблицу пользователей базы данных.
7. Система сразу выполняет автоматический вход (без отдельного экрана
   подтверждения) и переходит в личный кабинет пользователя.

## Сценарий для задачи «Авторизация в системе»

1. Пользователь открывает страницу авторизации (вкладка «Войти» по
   умолчанию).
2. Система отображает форму авторизации.
3. Пользователь вводит адрес электронной почты и пароль.
4. Пользователь нажимает кнопку «Войти».
5. Система проверяет введённые учётные данные и статус учётной записи
   (вход блокируется, если статус `BLOCKED`).
6. Система выдаёт JWT-токен и предоставляет пользователю доступ к
   функциям веб-приложения в соответствии с его ролью.
7. Система перенаправляет пользователя на главный экран, соответствующий
   роли: список исследований — для `USER`, рабочий стол генеалога — для
   `GENEALOGIST`, панель администратора — для `ADMIN`.

## Сценарий для задачи «Создание генеалогического профиля»

1. Пользователь открывает раздел «Мои исследования» (бывший «Профили»).
2. Система отображает список имеющихся исследований и форму создания
   нового исследования (форма постоянно видна над списком, отдельной
   кнопки, открывающей форму, нет).
3. Пользователь заполняет поле «Название» и нажимает кнопку «Создать».
4. Система проверяет, что название не пустое.
5. Система сохраняет новую запись (статус `DRAFT`) в таблицу
   генеалогических профилей и добавляет карточку в начало списка —
   отдельного сообщения об успехе не выводится, результат виден сразу
   по появлению карточки.

## Сценарий для задачи «Добавление информации о родственнике»

1. Пользователь открывает нужное исследование и переходит на вкладку
   «Персоны» внутри страницы исследования (отдельного пункта главного
   меню «Персоны» нет — это вкладка одной общей страницы).
2. Система отображает список персон, привязанных к исследованию, и
   кнопку «+ Добавить».
3. Пользователь нажимает кнопку «+ Добавить».
4. Система отображает форму ввода данных о персоне.
5. Пользователь заполняет поля: фамилия, имя, отчество, девичья фамилия
   (только если пол — женский), пол, дата и место рождения, отметка
   «жив»/дата и место смерти (если не жив), примечания.
6. Пользователь нажимает кнопку «Сохранить».
7. Система проверяет корректность введённых данных.
8. Система сохраняет данные в таблицу персон базы данных.
9. Новая персона появляется в списке вкладки «Персоны».

## Сценарий для задачи «Редактирование информации о родственнике»

1. Пользователь выбирает персону в списке на вкладке «Персоны» —
   открывается отдельная страница персоны.
2. Система отображает полную карточку персоны.
3. Пользователь нажимает кнопку «Редактировать».
4. Система отображает форму редактирования с текущими значениями полей.
5. Пользователь вносит изменения.
6. Пользователь нажимает кнопку «Сохранить».
7. Система проверяет корректность данных и обновляет запись в таблице
   персон базы данных.
8. Карточка персоны обновляется отображением новых данных — отдельного
   сообщения об успехе нет.

## Сценарий для задачи «Удаление информации о родственнике»

1. Пользователь открывает страницу нужной персоны.
2. Пользователь нажимает кнопку «Удалить персону».
3. Система запрашивает подтверждение через системное диалоговое окно
   браузера (а не отдельную форму подтверждения).
4. Пользователь подтверждает удаление.
5. Система удаляет персону и все связанные с ней факты и связи из базы
   данных.
6. Пользователь перенаправляется на страницу исследования — отдельного
   сообщения об успехе нет.

## Сценарий для задачи «Добавление родственной связи»

1. Пользователь переходит на вкладку «Связи» внутри страницы
   исследования (не отдельный раздел меню).
2. Система отображает список существующих связей исследования и кнопку
   «+ Добавить связь».
3. Пользователь нажимает кнопку «+ Добавить связь».
4. Система отображает форму создания связи.
5. Пользователь выбирает исходную персону, целевую персону и тип связи:
   «Родитель–ребёнок», «Супруги» или «Иная» (для «Иной» дополнительно
   указывается текстовое описание и, опционально, как отображать связь
   на дереве — как родственную, супружескую или сестринскую/братскую).
6. Пользователь нажимает кнопку «Сохранить».
7. Система проверяет: отсутствие цикла в родительских связях, что у
   персоны не более двух родителей, отсутствие дубликата связи.
8. Система сохраняет связь в таблицу родственных связей базы данных.
9. Связь появляется в списке; удаление связи выполняется аналогично
   удалению персоны — через подтверждение в диалоговом окне браузера
   (этого действия не было в старой версии сценария).

## Сценарий для задачи «Добавление генеалогического факта»

1. Пользователь открывает страницу нужной персоны.
2. Система отображает карточку персоны с подразделом «Факты» на той же
   странице (не отдельным переходом).
3. Пользователь нажимает кнопку «Добавить факт».
4. Система отображает форму добавления факта.
5. Пользователь указывает тип факта (рождение/смерть/брак/проживание/
   служба/заметка), дату, место, текстовое описание и достоверность
   (непроверено/гипотеза/вероятно/подтверждено).
6. Пользователь нажимает кнопку «Сохранить».
7. Система сохраняет факт в таблицу фактов базы данных.
8. Факт появляется в списке фактов персоны.

## Сценарий для задачи «Формирование архивного запроса»

1. Пользователь переходит на вкладку «Запросы» внутри страницы
   исследования.
2. Система отображает список архивных запросов исследования и форму
   создания нового запроса.
3. Пользователь заполняет поля «Название запроса» и «Цель запроса» и
   нажимает кнопку «Сформировать».
4. Система создаёт запись со статусом `PREPARED` (а не «черновик» —
   статус `DRAFT` в текущей реализации не используется как стартовый).
5. Дальнейшая обработка запроса проходит по статусной модели:
   `PREPARED → SENT → IN_PROGRESS → (NEEDS_CLARIFICATION) →
   RESPONSE_RECEIVED → COMPLETED/CANCELLED` — переходы выполняет
   назначенный администратором генеалог из своего рабочего стола.
6. Дополнительно пользователь может воспользоваться мастером
   «Сформировать архивное обращение» — выбрать шаблон архива (общий,
   военный, ЗАГС, медицинский, кадровый, по месту жительства или
   произвольный) и пройти 4 шага заполнения полей шаблона, чтобы
   получить готовый документ-обращение для отправки в архив. Этого
   функционала в исходном сценарии не было.

## Сценарий для задачи «Просмотр статуса архивного запроса»

1. Пользователь открывает вкладку «Запросы» внутри исследования.
2. Система отображает список запросов пользователя.
3. Пользователь выбирает нужный запрос — открывается отдельная страница
   запроса.
4. Система отображает карточку запроса: текущий статус, дату создания,
   историю изменения статусов, результаты обработки (сводка, найденные
   сведения, источники, рекомендации), прикреплённые документы и блок
   уточнений (если генеалог запрашивал дополнительную информацию).
5. Назначенный генеалог в текущей реализации виден только в панели
   администратора — на странице запроса для пользователя-владельца это
   поле не выводится явно (расхождение со старой версией сценария,
   которое стоит либо устранить в интерфейсе, либо держать в виду как
   текущее ограничение).

## Сценарий для задачи «Просмотр генеалогического древа»

1. Пользователь открывает исследование и нажимает кнопку «🌳 Дерево»
   на странице исследования (не отдельный пункт главного меню).
2. Система извлекает из базы данных персон и родственные связи
   выбранного исследования.
3. Система строит структуру древа: вычисляет поколения, группирует
   супружеские пары и одиночных родителей в «семейные» узлы, раскладывает
   узлы по уровням через библиотеку Dagre и маршрутизирует связи
   ломаными линиями без пересечения карточек.
4. Система отображает пользователю визуализированное и интерактивное
   древо: клик по персоне открывает боковую панель с карточкой, центр
   просмотра плавно смещается к выбранному узлу.

*Этот сценарий — единственный, который полностью совпадает с
первоначальным описанием.*

## Сценарий для задачи «Просмотр уведомлений»

1. Пользователь нажимает на иконку колокольчика в верхней панели
   приложения (отдельного раздела «Уведомления» в меню нет — это
   выпадающая панель в хедере).
2. Система отображает список уведомлений пользователя.
3. Пользователь выбирает нужное уведомление.
4. Система отображает текст уведомления и переходит к связанному
   объекту (например, к архивному запросу или готовой книге).
5. Система помечает уведомление как прочитанное (поле `read_at`).
   Дополнительно доступна кнопка «Прочитать все» для массовой отметки —
   этого действия не было в исходном сценарии.

## Сценарий для задачи «Формирование генеалогической книги»

1. Пользователь переходит на вкладку «Книга» внутри страницы
   исследования.
2. Система отображает настройки генерации (стиль повествования —
   тёплый/документальный/краткий; включать ли непроверенные факты и
   гипотезы) и кнопку «Сформировать книгу».
3. Пользователь нажимает кнопку «Сформировать книгу».
4. Система запускает формирование **асинхронно** в фоновой задаче:
   статус книги переходит `PENDING → IN_PROGRESS`; для написания
   текста используется нейросеть YandexGPT на основе данных профиля,
   фактов, связей и документов (либо детерминированный шаблон, если
   ключ YandexGPT не настроен).
5. Фронтенд опрашивает статус каждые 2 секунды, пока он не станет
   `SUCCEEDED` или `FAILED`.
6. После завершения система сохраняет итоговый файл (HTML-документ) и
   создаёт пользователю уведомление о готовности книги (тип
   `BOOK_READY`, связь со сценарием «Просмотр уведомлений»).
7. Пользователь может просмотреть и скачать готовый файл со страницы
   исследования.
